# Music Video Auto-Mix v2

> For: `versions/music_video.html` + `versions/music_video_mtv.html` (both share the same `client/automix.client.js` core)
> Generated: 2026-09-20
> Status: **proposal — apply nothing until scope agreed**

## Baseline (current state)

The automix pipeline is:

```
Audio.feat (bass/mid/treb/beat)
  → SWR_ANCHOR_EMBED.featuresToCoords  →  (warmth, intensity)
  → SWR_ANCHOR_MAP.neighbours(coords, N)  →  N nearest anchor presets
  → blendAnchors()                       →  weighted-average fx_state (8 fields)
  → drift(beat-scaled)                   →  tiny ±0.005..0.015 random walk
  → window.SWR._fxOverride               →  GLSL render reads each frame
```

Orchestrator: 2000ms `setInterval` in `versions/music_video.html:3210`. Toggle = `#automix-toggle` button or `A` key. Persistence: `localStorage.swr.automix.enabled` + `swr.automix.lastMix.v1` (debounced 1s).

Tests already exist: `scripts/check-automix-smoke.mjs`, `check-automix-unit.mjs`, `check-last-mix-unit.mjs`.

### What's already wired but unused

- `client/section-detector.client.js` — classifies intro/verse/prechorus/chorus/breakdown/outro with confidence
- `client/section-scheduler.client.js` — tweens chapter state over N beats (smoothstep) on section change
- `Audio.feat` carries `bpm, rms, centroid, onset` — automix only reads bass/mid/treb/beat

The automix **ignores song structure entirely**. That's the biggest gap.

### Prior art

`docs/AUTOMIX-FADE-AUDIT-2026-09-09.md` covered `Layers.autoMap()` abruptness + audio gain fades. Those fixes already landed in `engine-core.client.js:349-395` (`Audio.fadeTo/fadeIn/fadeOut`). We're now improving the *blend evolution*, not the transitions.

## Phase 1 — Speed & Responsiveness

**Why**: The 2000ms tick is too coarse for music. Chorus hits, drops, and breakdowns all happen in <500ms. The blend feels laggy relative to the song. Plus the blend snaps into place — no smoothing.

**Changes**

1.1. **Adaptive tick interval** — slow during quiet sections (intro, breakdown), fast during chorus/drop.
   - New `Audio.feat` inputs: `rms`, `centroid`, `onset`.
   - Compute `intensity = clamp(rms * 1.5 + onset * 0.8, 0, 1)`.
   - Map to interval: `intensity=0 → 3000ms`, `intensity=1 → 500ms`, linear.
   - In `automix.tick()`: clear and reset `setInterval` to the new cadence each tick.

1.2. **Smooth interpolation** — store `fromPreset` + `toPreset` + `t0` + `duration`. Each frame the render reads an interpolated value. Replace the snap with a 1s ease-out ramp.
   - Easiest path: keep `_fxOverride` as the *target*. Add `_fxFrom` + `_fxT0`. In `requestAnimationFrame` (or in the existing render loop) compute `current = lerp(_fxFrom, _fxOverride, smoothstep((now - _fxT0) / 1000))`.
   - Where to hook: `engine-render.client.js` reads `_fxOverride` — patch the read site, not the automix code.
   - Free win: scene transitions feel continuous instead of jumpy.

1.3. **Beat-phased drift** — mutations land on downbeats, not random times.
   - Use `Audio.feat.beatPulse` to trigger a mutation on the rising edge.
   - Drop the per-tick random walk. Apply drift on every detected beat, scaled by `onset * 0.02` (so weak beats drift gently, strong hits jolt).

**Tests**
- `check-automix-smoke.mjs`: tick interval lands in [500ms, 3000ms] range across varied features.
- `check-automix-unit.mjs`: add test for `lerp`/`smoothstep` blend math.

**Risk**: low. Worst case: visual feels too fast. Easy revert.

## Phase 2 — Musical Intelligence (section-aware)

**Why**: The biggest gap. The song has detectable sections, and a chorus should pull a different anchor pool than a breakdown. Currently automix is blind to this.

**Changes**

2.1. **Wire `SWR_SECTION`** — poll each tick, store current section.
   - Load `client/section-detector.client.js` in `music_video.html` (it's already in the repo, just not `<script src=...>`ed here).
   - On each tick: `section = SWR_SECTION.detect(Audio.feat)`.
   - If section changed since last tick: emit a `swr-automix-section-change` event (UI can react).

2.2. **Per-section anchor pools** — different sections prefer different parts of the gradient.
   - Add a small config map in `client/automix.client.js`:
     ```
     POOL_BIAS = {
       intro:     { warmth: [0.4, 0.6], intensity: [0.0, 0.4] },
       verse:     { warmth: [0.3, 0.7], intensity: [0.3, 0.6] },
       prechorus: { warmth: [0.4, 0.7], intensity: [0.5, 0.8] },
       chorus:    { warmth: [0.2, 0.8], intensity: [0.6, 1.0] },
       breakdown: { warmth: [0.5, 0.9], intensity: [0.0, 0.3] },
       outro:     { warmth: [0.3, 0.6], intensity: [0.2, 0.5] },
     }
     ```
   - When picking `n` nearest anchors, filter the anchor map to those inside the section's bias box first. If < 2 candidates, fall back to unfiltered.
   - Confidence < 0.5 → treat as 'verse'.

2.3. **Richer feature embedding** — use centroid in addition to bass/mid/treb.
   - Extend `SWR_ANCHOR_EMBED.featuresToCoords` (or add a new `featuresToCoordsV2`) to take `centroid` and `onset`:
     - `warmth = clamp(0.5 + (bass - treb) * 0.4 + centroid * 0.2, 0, 1)`
     - `intensity = clamp(mid * 0.6 + treb * 0.3 + rms * 0.2, 0, 1)`
   - Keep the v1 function for backward-compat (other callers); v2 used only by automix.

2.4. **BPM-locked anchor cycling** — at high BPM, also rotate through 3–4 anchors at bar boundaries so the visual doesn't lock to one.
   - On every `n`th beat (where `n = round(bpm / 30)`, i.e.4–8 beats at common tempos), nudge the blend 25% toward a *randomly chosen different neighbour*.

**Tests**
- `check-automix-unit.mjs`: `POOL_BIAS` filter returns expected subsets for synthetic anchor maps.
- `check-automix-smoke.mjs`: with simulated section sequence, verify blend evolves differently per section.
- Update `check-automix-unit.mjs` to cover `featuresToCoordsV2`.

**Risk**: medium. If `SWR_SECTION.detect` produces noisy classifications, automix will jitter. Mitigate with confidence threshold + section-change hysteresis (must be stable for 2 ticks before switching).

## Phase 3 — Visual Evolution

**Why**: The drift amplitude (±0.005..0.015) is tiny — the visual evolution isn't dramatic enough. And if a song sits on the gradient for a long stretch, automix locks onto one blend forever.

**Changes**

3.1. **Larger bounded drift** — bump baseline amplitude. Phase 1.3 already beat-times it; here we just increase the constant.
   - `amplitude = 0.01 + 0.02 * beat` (was `0.005 + 0.01 * beat`). 2× more motion.

3.2. **Stuck detection** — if the blend hasn't moved ≥ 0.05 (Euclidean in fx_state 8-space) for 12 seconds, force a "scene change":
   - Pick a random anchor 2–3 hops away in the gradient (via `SWR_ANCHOR_MAP.neighbours(trackCoords, 1)` then `neighbours(theirCoords, 3)` — second-degree search).
   - Snap toward it for 2 seconds, then resume normal blending.

3.3. **Anti-pattern detection** — if `centroid` variance < 0.05 for 8 bars (ambient pad / drone), inject curated mutations every 4 bars (pick 1 of 3 preset "moods": wider chromatic, denser grain, stronger glow).

**Tests**
- `check-automix-unit.mjs`: stuck detection fires after 12s of static blend.
- `check-automix-unit.mjs`: anti-pattern fires on synthetic flat-centroid input.

**Risk**: medium. Stuck detection could fire on legitimately quiet songs. Mitigate with a `?forceEvolve=off` query param to disable.

## Phase 4 — UX

**Why**: The toggle shows ON/OFF and that's it. Users can't see what's happening, can't save a great blend, can't freeze to inspect.

**Changes**

4.1. **Debug panel** — collapsible, bottom-right.
   - Shows: current coords, dominant anchor id, blend weights (bar viz), section name + confidence, last drift delta, beat-rate (blends/min).
   - Toggle: `D` key, or a small ⓘ button next to `#automix-state`.
   - Hidden by default. Persisted (`localStorage.swrc.automix.debugOpen`).

4.2. **Freeze button** — `#automix-freeze` next to the toggle.
   - ON: stops ticking but keeps current blend. The synth pill shows "frozen".
   - OFF: resumes normal ticking from current audio.

4.3. **Save blend as manual preset** — `#automix-save` button.
   - Prompts for name (or auto `auto-<timestamp>`), writes to `localStorage.swrc.presets.user.v1` (already used elsewhere).
   - On recall: bypasses automix, applies the saved preset directly.

4.4. **"Lock to nearest anchor" mode** — `#automix-lock` button.
   - When ON: automix picks the closest single anchor (no blending), no drift. Useful for sections you want to control tightly.
   - Off: resume blending.

**Tests**
- New `verify:automix` Puppeteer suite: load song, toggle automix on, verify panel opens, click freeze, verify tick stops, click save, reload, verify blend restored.

**Risk**: low. Pure additive UI. Each control has its own toggle.

## Phase 5 — Coverage

**Why**: Phases 1–3 change core behavior. We need unit + e2e coverage before declaring victory.

**Changes**

5.1. **New unit tests** in `scripts/check-automix-unit.mjs`:
   - Section-pool filtering
   - Beat-phased drift triggers
   - Stuck detection
   - Anti-pattern detection

5.2. **New smoke test** `scripts/check-automix-smoke.mjs` additions:
   - Synthetic section sequence → blend evolves differently per section
   - Sustained flat input → blend escapes via anti-pattern within 30s

5.3. **New verify script** `verify-automix.mjs`:
   - Load demo song in Puppeteer
   - Toggle automix on
   - Verify `_fxOverride` changes ≥ 3 times in 20s
   - Verify synth pill updates
   - Verify debug panel toggles open/close
   - Verify freeze stops ticking
   - Verify save+reload restores

5.4. **Wire `npm run verify:automix`** in `package.json`.

**Risk**: none — pure test additions.
